# EXP27 真实服务检查覆盖不足：失败复盘与修复计划

2026-10-30 审核结论：EXP27 的一轮官方形状诊断完成了256个请求，零失败，32次真实模型 logits 的精确 mask / RNG 检查全部通过；但没有覆盖真实 B64 的对照检查，准入条件失败，后续正式四轮性能测试未启动。当前最优版本仍为 EXP20。不能将微基准的66.73%耗时下降写成端到端收益。

## 发生了什么

运行目录为 `20261029_203604_shadow`，固定插件提交为 `2a4cf99f5a765dc7de3a3337303e91183bc9decd`，FlagGems 为 `de958ddfc4deeb43d6c94bb8652a3d4d3bc905fe`。自动归档提交为 `d5437268cd536214363ab4dac3038fb69c810c86`。

| 北京时间（10月29日） | 日志证据 |
|---|---|
| 20:41:18.649 | 编译、smoke、启动路由检查完成，记录 workload_start |
| 20:42:41 | B17，第一次 shadow 检查通过，p_min/p_max≈.95 |
| 20:43:12 | B32，第32次检查通过，耗尽全局配额 |
| 20:44:13 | 首次记录 B64，programs=64，candidate_calls=96 |
| 20:52:12 | 256请求诊断结束后，B64/.95 shadow 准入断言失败 |
| 20:52:16 | 自有服务清理完成，失败数据保存并自动推送 |

全部32次检查来自工作负载开始后，B17至B32各两次。根因是原实现的“全局前32次”采样策略无法保证覆盖逐渐增长到64的批量。不是预热耗尽配额；日志没有报告 mask 或 RNG 不一致。B64 的 grid 日志证明走到了候选入口，但不能代替该批量的逐元素对照，因此保留原准入失败结论。

原代码的限制为：

```python
do_shadow = shadow and _stats['shadow_checks'] < 32
```

服务控制器另行要求工作负载区间至少一次真实 B64、V130560、p≈.95 的 mask 精确相等和 RNG 不变记录。两个条件的覆盖设计不匹配；不能通过删除控制器断言来补救。

## 已验证和未验证的边界

诊断请求参数保持官方内层命令：4096输入、1024输出、并发64、256请求、random数据集、ignore-eos，不覆盖temperature/top-p。实际输入token为1,048,576，输出为262,144。原始日志中的2100.13 total tok/s属于开启shadow的单轮诊断，还含新服务首轮效应，不纳入正式成绩，也不与四轮弃首的基线计算回归或收益。

启动时保存的路由记录显示42个原始MLP块，gate/up与down未转换布局；KV容量522,352 tokens。归档共有52条top-p active grid记录，B64实际使用64个program，scratch为64行、33,423,360字节。但失败发生在最终的top-p元数据与完整路由检查之前，不能称整个接线审核已经通过。

此前EXP26微基准140项、EXP27入口30项检查通过的记录仍有效；它们不能补齐本次缺失的真实B64证据。完整模型任务精度仍按用户要求暂缓。

本次离线审核对自动归档中的14个文件逐一核验SHA-256，复算请求数、token数与事件顺序。离线审核时服务器不可访问，未重新校验服务器原始文件及编译缓存；13:20连接恢复后，另行保存服务器原始文件复核记录（不覆盖离线审核范围）。归档日志经过脱敏和空白规范化，因此分析使用带时间戳的事件，未把原始日志字符offset直接套到归档文本。

## 修复草稿与下一次执行

在独立r1目录准备了诊断补丁：B17..64各保留两次检查，总计最多96次；通过新的arm文件开关，预热结束、记录workload_start之后才允许消耗配额。新服务拒绝已有的arm文件，避免误用上次状态。shadow关闭时不创建预算对象，也不访问该文件。候选kernel、grid、采样参数与RNG算法不改。

11项CPU回归通过，覆盖此前的B17..32耗尽序列、晚到B64仍有额度、预热B64、旧arm文件、配额上限和关闭分支。该补丁尚未应用到服务器或生产分支，controller的arm接线、设备检查和正式性能仍待完成。补丁和测试作为实验草稿保存，设备验证通过后再推推理代码fork。
