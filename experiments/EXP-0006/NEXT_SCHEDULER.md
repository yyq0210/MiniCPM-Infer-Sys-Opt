# 融合之后的调度实验准备

这里只记录已核实的证据与后续假设，尚未接入调度优化，也没有 KV 压缩性能或质量结论。

EXP-0005 完整官方测评前后的 `vllm:num_preemptions_total` 从 0 增至 16。
这覆盖 4K 与 16K 两组各四轮，不能仅凭总计将 16 次都归因到 16K。
服务文字日志未包含抢占提示，因此以 Prometheus 计数器为准。
后续分组运行各自保存测前与测后指标，可以确认抢占属于哪个负载。

安装版本中的实现路径：

- `vllm/v1/core/sched/scheduler.py:525`：为正在运行的请求申请块，失败后会抢占请求。
- `scheduler.py:874`：新请求准入，传入 `full_sequence_must_fit`、`reserved_blocks` 和 `has_scheduled_reqs`。
- `scheduler.py:1116`：被抢占请求释放块，已计算 token 数归零，随后重新排队；这带来重算。
- `scheduler.py:2335`：计算已在执行请求的剩余块需求，目前按现有序列长度计算。
- `vllm/v1/core/kv_cache_manager.py:363`：水位只作用于已有运行请求时的新请求/被抢占请求准入。
- `kv_cache_manager.py:372`：完整输入长度准入检查包含水位，但没有加 `reserved_blocks`。
- `kv_cache_manager.py:414`：当前分块实际分配检查才扣除 `reserved_blocks`。

因此，简单把 decode 未来增长量填进 `reserved_blocks`，不足以证明“新请求的完整输入不会侵占既有请求的增长空间”。
实验实现必须同时覆盖完整序列准入与当前分块分配，避免只保护第一个 prefill chunk。

下一阶段候选：为已运行请求和待准入请求的输出增长预留容量，减少因为未来 decode 增长而产生的抢占和重算。
分别考虑完整 `max_tokens` 上界和有限增长窗口；前者更保守，可能降低并发，后者仍可能发生抢占。
不能只用“抢占减少”判断优劣，必须同时报告吞吐、TTFT、TPOT/ITL、排队时间和最大有效并发。
固定官方服务参数；策略作为可回退的引擎代码实现，不暗改 benchmark 并发或请求长度。

实现前需要验证：

- 只在明确支持的单组 full-attention、单卡、无 speculative/KV connector 条件下启用。
- 用实际块分配器计算 prefix-cache 命中与共享块后的需求，不直接把逻辑 token 数当物理占用。
- 准入失败时不改变请求状态、缓存引用计数或已分配块。
- 首个请求不得因保留策略死锁；请求完成、取消、恢复与输出增长都能更新预留量。
- KV 内容、RoPE 绝对位置和注意力范围保持不变。

调度不会创造显存。若 64 条长请求的完整 KV 容量超过显存，仅调整队列无法让它们同时驻留。
KV 压缩属于后续独立阶段，必须证明实际回收物理块，并完成完整缓存对照、官方 MATH500 Level 3 和真正触发压缩的长文质量测试。
