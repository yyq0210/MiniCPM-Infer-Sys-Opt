# EXP-0007：为运行请求预留 KV 增长空间

状态：假设与实现准备；尚无性能或模型精度结论。

## 对照与假设

候选以 EXP-0006 的插件 `07d9fa0cfdc5f09db178e29508e3c0bcb5c1e908`、
FlagGems `484413ea0db18221dd9e63e742361d837df9ff13` 为父版本。
官方原始基线仍是插件 `13eb9be69ecc5b5ca4f79c44e9ee40081eaa1bf0`、
FlagGems `a7620cc191a0b42e040194622c5758b22a7a25dc`。
EXP-0006 16K 正在独立工作区测试；本实验不得改写其运行源码。

已知证据：

- EXP-0005 的完整 4K＋16K 测评共发生 16 次抢占，无法用合计归因到单组。
- EXP-0006 4K 四轮完成，测前/测后抢占计数都是 0。
- 当前 vLLM 的完整输入长度准入门槛，只检查新请求的当前完整序列。
  它没有为其他在运行请求的未分配输入块和未来输出增长持续预留空间。
- 被抢占请求的 `num_computed_tokens` 清零，会重新排队并重算。

假设：新请求准入前，利用真实 KV 块分配器计算“所有运行请求的剩余完整输入＋
最大输出增长＋新请求完整生命周期”的额外物理块需求，容量不足时暂缓新请求，
可以减少抢占重算。代价是可能更早排队、降低有效并发；收益必须以完整端到端数据判断。

## 实现边界

增加一个在原分配器之前执行的只读准入门槛；通过实例级代理保留原分配器的实际
分配、释放、prefix cache、事件和统计实现，不改共享 site-packages。
容量预测使用 `coordinator.get_num_blocks_to_allocate`，正确区分已引用的共享前缀块
和仍在空闲队列、命中后需要移出空闲队列的前缀块。

仅对明确支持的单组 full attention、单卡、无 speculative / KV connector /
多模态 / streaming session 的异步调度启用；不支持条件回退原逻辑。
已有 RUNNING 请求继续走原分配器；首个请求保留原准入逻辑，防止保守预留造成空转。
原 FCFS/priority 队列、请求长度、最大输出、采样、KV 内容和 RoPE 位置不变。

先测试完整 `max_tokens` 上界预留。有限增长窗口只作为后续候选，不预先宣称更优。
不使用隐藏的并发限制、缩短输入输出或修改官方 benchmark。

## 验证与评价

CPU 验证必须覆盖真实 KV 分配器：拒绝准入无副作用、完整输入与输出增长、分块
prefill、共享/可驱逐前缀、块边界、首请求、释放/取消后再准入、抢占后恢复、
异步占位 token 和不支持配置回退。另检查引擎确实选择新的 AsyncScheduler 子类。

GPU 测试在 EXP-0006 16K 和自动归档完成后串行执行。先检查引擎接入与原 42 层
融合/GQA 路径，再执行官方 4K/16K，每组四轮、弃首轮。保存准入统计、抢占、
排队、吞吐、TTFT、TPOT/ITL 和有效并发；不能只凭抢占下降宣布优化成功。

按用户要求，无损调度暂缓完整任务精度测试；仍需要运行和生命周期验证。
KV 压缩属于后续独立实验，必须做精度验证，本实验不删除或压缩任何 KV。
